# Dataverse browser connection troubleshooting — Public Beta v0.4

## Root cause found in uploaded deployment files

The user-supplied folder deployment/mightora-dataverse-tools contained flat HTML files named mgt_trace.html, mgt_metadata.html and so on. They were not published under a virtual folder such as mgt_/trace.html, yet the original script referenced ../ClientGlobalContext.js.aspx. For a flat web resource Microsoft documents ClientGlobalContext.js.aspx (no ../). The 404 left GetGlobalContext undefined, so every tool showed its preview/connection fallback rather than calling Dataverse.

Both versions now work:

- Flat resource: WebResources/mgt_trace.html → ClientGlobalContext.js.aspx
- Virtual directory: WebResources/mgt_/trace.html → ../ClientGlobalContext.js.aspx
- Cache/version-prefixed resource: /%7Bversion%7D/WebResources/mgt_trace.html → ClientGlobalContext.js.aspx

The script loads synchronously from the current Dataverse environment; it is never loaded on the public demo (?demo=1) or from a local file.

## How to verify after deploying updated web resources

1. Upload and publish the updated mgt_trace.html and mgt_environment.html into an unmanaged **development** solution. Replace the contents of the existing HTML web resources, retaining their exact logical names used by your model-driven app. The same applies to each tool.
2. Open the model-driven app. In the browser press F12 → Network, enable Preserve log, and reload the page.
3. Filter for ClientGlobalContext.js.aspx. It should return HTTP 200 (not 404). If the script is missing/blocked, inspect its Request URL, response, and the published web-resource name. Do not try parent.Xrm for SiteMap app pages.
4. In the same web resource page, open the Console and evaluate: typeof GetGlobalContext. It should return "function".
5. For a permitted test user, run the following read-only API test in that page's DevTools:
   
   const org = GetGlobalContext().getClientUrl();
   fetch(org + "/api/data/v9.2/WhoAmI()", {
     credentials: "same-origin",
     headers: { Accept: "application/json", "OData-Version": "4.0", "OData-MaxVersion": "4.0" }
   }).then(async response => ({ status: response.status, body: await response.text() }))
     .then(console.log);
   
   This returns a user ID (if authorised). Do not share IDs publicly or paste secrets into third-party tools.
6. A 401 or 403 response is an authorisation/privilege issue rather than a helper-path issue. If the script loads but the API call still fails, check the actual requested origin, model-driven app navigation host, Content Security Policy, and environment access.
7. Confirm metadata tables load in Metadata Explorer and record results load in Plugin Trace Explorer, using a development user with appropriate table privileges.

## Three integrated Mightora tools

The original self-contained Dataverse editions are built from upstream pinned commits and copied into the toolkit:

- REST Studio → mgt_rest.html. Current-origin API only; write methods have an explicit confirmation step. REST uses the Microsoft helper for context, and supports a version-prefixed WebResources URL.
- FetchFlow → mgt_fetchflow.html. Uses Microsoft GetGlobalContext for connection and same-origin Web API for metadata/FetchXML; no dependency on parent.Xrm in a SiteMap page.
- Solution Explorer → mgt_solution_explorer.html. Uses its own same-origin Dataverse adapter to inspect available solutions. ExportSolution requires appropriate rights and should be tested separately.

Install the THREE upstream web resources as flat names mgt_rest.html, mgt_fetchflow.html and mgt_solution_explorer.html. They have CSPs generated by their maintainers; changing scripts after build would invalidate cryptographic hashes. The toolkit integration builds and validates the upstream source without introducing remote scripts into a customer environment.

## What your uploaded ZIP actually contains

The original deployment/mightora-dataverse-tools.zip was inspected: ten HTML files, README.md and LICENSE. It had **no** Other/Solution.xml, customizations.xml, app module or root component metadata. It cannot be imported into Power Apps as an unmanaged solution. Its rebuilt successor includes fourteen self-contained HTML files and a manifest declaring that it is a web-resource distribution.

An actual solution source obtained with pac solution unpack should have Other/Solution.xml and Other/Customizations.xml (XML layout), or the Dataverse Git integration YAML layout with solutions/<name>/solution.yml and related files.

To include these tools in the **model-driven app itself**, create the missing three HTML resources and add pages in the app designer (or provide a genuine exported unmanaged solution to modify). Then export and unpack from Dataverse and run pac solution pack using that genuine source. Merely placing HTML files in a folder or ZIP does not add app navigation pages or solution components.
